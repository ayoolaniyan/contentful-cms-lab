### Block 2 results — `include`, caching, and staleness

**`include: 0` breaks link resolution — seen live, here's why.** Fetched the same article via the CDA with `include: 0` and `include: 2` and diffed the `author` field:
- At `include: 0`, `fields.author` is just `{ sys: { type: "Link", linkType: "Entry", id: "1inVQ4nO1BdUtLgSbUl4K5" } }` — no `.fields` at all, just a pointer.
- At `include: 2`, the same field is the fully resolved Author entry — `.fields.name`, `.fields.slug`, everything.

Reference fields in Contentful's response are never inlined by default; `include` tells the CDA how many link-hops deep to resolve and embed inline in the same payload (0 = don't resolve, so you get raw `Link` stubs back). This is exactly the failure mode `mapper/index.ts`'s `authorRef()` guards against — it checks `author.sys.type === "Link"` and returns `{ id, name: "" }` instead of assuming `.fields` exists, because at low `include` depth (or a reference to an unpublished/deleted entry, which behaves the same way even at high `include`) that assumption breaks silently: `field.fields?.name` just becomes `undefined` via optional chaining rather than throwing, so an under-`include`d fetch doesn't crash, it quietly ships blank author names.

**Caching/staleness trade-off (Block 2 vs. Block 5).** The direct-CDA pages (`web/app/articles/*`) use `cache: "no-store"` implicitly (no explicit fetch cache config, `dynamic = "force-dynamic"`) — every request re-hits the Contentful CDA. That's the simplest thing that's always correct: zero staleness window, but latency and CDA rate-limit exposure scale directly with your traffic, and you're paying a network round-trip to Contentful on every single page view. `/content/articles` on the owned delivery API (Block 5) does the opposite trade: `cache-control: public, max-age=30` (`sync-service/src/delivery.ts`), so reads are fast and cheap regardless of traffic, but there's now a real staleness window — up to 30s where a client could see pre-publish data, compounded by whatever publish-to-store lag the sync path already has (measured in the Block 6 results above). The right choice depends on which cost you can afford: no-store is fine at low traffic where an extra CDA round-trip is cheap; once traffic or CDA rate limits make that expensive, you trade a bounded staleness window for speed and pay for it with cache invalidation complexity (or, as here, just a short TTL and eventual consistency instead of active invalidation).

## Block 4 — Backfill + reconciliation
Webhooks for latency, reconciliation for correctness, one mapper for both.
Reconciliation ran on a schedule — a Cloud Scheduler job hitting a Cloud Run job every few minutes in GCP terms, or a Kubernetes CronJob. Webhooks gave sub-second freshness; the sweep was the safety net, and its lag budget was minutes, not seconds. The token is persisted, so each run only fetches deltas — cheap enough to run often without hammering the API

### Block 4 results — rate limits and scheduling

**The actual numbers** (Contentful's documented technical limits, current as of writing):
- Content Delivery API (CDA): 55 req/s on the free plan, 78 req/s on paid plans, no burst allowance ("no burst, no hourly buffer" — it's a hard per-second cap, not a token bucket with slack).
- Content Management API (CMA): 7 req/s free, 10 req/s paid — roughly an order of magnitude tighter than the CDA, which matters because `backfill`/`reconcile` read via CDA but any future write-back path would be CMA-bound.
- Every response carries `X-Contentful-RateLimit-Second-Limit` / `-Second-Remaining` / `-Hour-Limit` / `-Hour-Remaining` / `-Reset`; a 429 also carries `Retry-After`.

**What backfill actually does to them.** Checked the installed SDK source directly (`contentful-sdk-core`'s `rate-limit.js`) rather than assuming: the `contentful` client already wraps every request in a retry interceptor with `retryOnError: true` by default, up to 5 attempts, and on a 429 it reads `x-contentful-ratelimit-reset` off the response and sleeps exactly that long (plus jitter) before retrying — so a naive `getEntries` loop doesn't need hand-rolled backoff, the SDK already has it.

More importantly, `backfillType()` in `src/scripts/backfill.ts` is a single sequential `while` loop — one `await cda.getEntries(...)` at a time, `PAGE_SIZE = 100`, no concurrency. At the space's current size (2 authors, 2 articles, 0 banners) that's 3 requests total, one page per content type. At production scale — say 5,000 articles — that's 50 sequential awaited requests; network round-trip latency alone (tens to low-hundreds of ms per call) keeps the effective rate well under even the free tier's 55 req/s, so the loop is self-throttling by construction. The only way to actually hit the limit is to parallelize the content-type loop (`Promise.all` across `CONTENT_TYPES`) or run concurrent backfill jobs — deliberately not doing that here, since correctness (never missing a page from a bad race) is worth more than a few seconds of runtime on a one-off job.

`reconcile.ts` is even cheaper against the limit: `cda.sync()` with a persisted token is one API call per run when there's nothing new (confirmed live — three consecutive delta runs each did exactly one request and returned in well under a second), and only pages further if there are actually many deltas to walk. Its cost against the rate limit doesn't grow with space size, only with how much changed since the last run.

**Scheduling answer.** Reconcile every 2–5 minutes via Cloud Scheduler → Cloud Run job (or a Kubernetes CronJob): frequent enough that the "lag budget is minutes, not seconds" promise holds even if a run or two fails, cheap enough (1 request when idle) that running it every 2 minutes is ~0.008 req/s average — nowhere close to needing its own rate-limit conversation. Backfill is a one-off/rare operation (initial load, or recovering from a corrupted store), not something to schedule recurring; if it ever needed to run against a much larger space, the fix would be spacing pages with a small delay or trusting the SDK's built-in 429 backoff, not adding concurrency.

**Missed-publish healing and deletion-while-down — verified by code inspection, not live.** Making an actual publish/delete against the space to watch these react required the Contentful Management API, and `CONTENTFUL_MANAGEMENT_TOKEN` is rejected by Contentful itself (401 `OrganizationAccessGrantRequired`, confirmed with a direct `curl` against `api.contentful.com`, not just the SDK) — so this was traced through the code instead of exercised end-to-end. Regenerate/grant org access on that token to close the loop later.
- *Missed publish healed by reconciliation:* `reconcile.ts` applies every entry in `cda.sync()`'s `result.entries` through the exact same `mapEntry` → `upsertEntry` path the webhook uses (`src/scripts/reconcile.ts:39-49`, mirroring `processor.ts`'s publish branch). Contentful's sync diff includes any entry that changed since the stored token regardless of whether a webhook fired for it, and `upsertEntry`'s `where content_entries.revision <= excluded.revision` guard means replaying an already-applied change is a safe no-op — so a publish our webhook dropped gets picked up and applied on the next reconcile run, through the identical mapping code, by construction.
- *Deletion while the service was down:* `result.deletedEntries` comes from Contentful's own sync log, not from our webhook, so it isn't affected by our uptime — a deletion made while nothing was listening still shows up the next time reconcile runs and calls the token forward. `reconcile.ts:51-54` calls `deleteEntry(d.sys.id)` for each one, which is a plain `delete ... where entry_id = $1` (`store.ts:31-33`) — safe even if the row is already gone. This exact code path was partially exercised live already: the first delta run after a fresh `--initial` sync surfaced one real `deletedEntries` item from Contentful's sync log (see reconcile results above), and `deleteEntry` ran against it without error.

## Block 5 — Own delivery API + frontend flip
Add GET /content/articles and GET /content/articles/:slug serving from Postgres. Flip the Next.js data layer from the Contentful SDK to your API — ideally behind the same fetch interface so the components don't change at all.
- What owning the store bought: availability independence from Contentful's API; cross-source querying and filtering in SQL; a delivery contract we control, so a CMS swap doesn't break consumers; and full control of caching and invalidation.
- What it cost: eventual consistency (publish-to-visible lag, which is measured in Block 3); a store to operate and back up; a sync path that can drift, needing reconciliation; and drafts must bypass it entirely via the Preview API.
- When you'd skip it: greenfield with a single content source and no existing store — pull-through with CDN caching and webhook-triggered invalidation is dramatically less machinery, and you build the sync only when you need multi-source queries or provenance-independent delivery.

## Block 6 — Production hardening
Retries with backoff on the processor; after N failures write to sync_failures with the error and payload — your dead-letter path.
Structured logging (pino) with entry ID on every line; log the publish-to-store lag (Contentful's sys.publishedAt vs your updated_at) — the health metric editors actually feel.
Table-driven tests for the mapper: valid entry, missing optional field, unresolved reference, malformed rich text, unknown extra field (must be ignored — your "additive changes are safe" answer). One idempotency test: process the same event twice, assert one row, same state.
Interview payoff: monitoring, failure handling, and the model-evolution answers — plus a test suite you can describe concretely.

### Block 6 results — observed numbers and alerting rationale

**Publish-to-store lag.** The original plan was to log `sys.publishedAt` (Contentful) vs `synced_at` (ours). In practice the Content Delivery API never returns `sys.publishedAt` at all — a live entry's `sys` only carries `createdAt`, `updatedAt`, `publishedVersion`, and `revision` (confirmed by fetching real entries and printing the raw `sys` object). The processor fetches through the CDA (fetch-on-notify, not the webhook payload), so `mapEntry` was silently computing `lagMs: null` on every single event. Fixed by mapping `publishedAt` from `sys.updatedAt` instead — that's the closest signal CDA actually exposes, and it moves at publish time for the normal edit-and-publish flow. Caveat worth remembering in an interview: `updatedAt` also moves on non-publish saves, and doesn't move at all on a no-op republish, so it's a proxy, not a ground truth — the Management API's `sys.publishedAt` would be the accurate source if this needed to be exact.

**What "lag" means once you separate the two things it was conflating:**
- *Our own processing latency* — webhook received → CDA fetch → mapped → written to Postgres. Measured directly from real webhook calls against this service (four concurrent publish events, local Docker Postgres, live CDA fetch): **134ms, 196ms, 222ms, 231ms** (~196ms average). This is the number that answers "how fast does a publish show up in our store," and it's fully within our control.
- *Content-side staleness* (`updatedAt` → `synced_at`) — dominated by how long ago an entry was last edited before this sync ran, not by system health. Not useful as a health signal on its own.

**What broke and what the fix looked like (the DLQ story):** `mapArticle` had a `if (!f.publishedDate) throw` guard for a field that turns out not to exist anywhere on the real Article content type (confirmed by listing live entries' field keys: `title, slug, body, author, heroImage, tags` — no `publishedDate`, matching Block 1's original model). Every real article publish was mapping-failing and landing in `sync_failures` with `error: "article missing publishedDate"`. Removed the bogus requirement, then ran `pnpm dlq`, which replayed the queued failure through the same `processEvent` path, synced it successfully, and cleared the DLQ row — `recovered 1, still failing 0`.

**Alerting rationale.** Three signals, in priority order:
1. **`sync_failures` count > 0 and growing** — the DLQ is the correctness safety net; any row in it means an entry is silently out of date in our store. Alert on non-zero count with a short debounce (a single transient failure self-heals via retry-with-backoff before it ever reaches the DLQ, so anything that lands there already exhausted 3 attempts and needs a human).
2. **`lastReconcileAt` age** — reconciliation is the sweep that catches whatever webhooks miss (dropped events, tunnel flakiness, restarts during in-flight processing). Its lag budget is minutes, not seconds, so alert if it hasn't advanced in longer than ~3x its schedule interval — that's a stuck or crashed reconcile job, not just a slow one.
3. **Processing-latency p95** (webhook received → synced) — the ~200ms baseline above is the healthy number; alert on sustained multiples of that (not single-event spikes, which are just GC pauses or a slow CDA response) since a persistent climb usually means Postgres contention or CDA rate-limiting, both of which matter before they become customer-visible.

Deliberately not alerting on raw `lagMs` (`updatedAt`-based) — it reflects editorial cadence, not system health, and would page someone for "nobody published anything in the last hour," which is noise.
